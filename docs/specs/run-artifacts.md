# Run Artifacts

**Type:** spec · **Status:** draft · **Updated:** 2026-04-22
**Depends on:** DDR-025, DDR-031, types.md §5–6, workflow-execution.md §Run artifacts, validation.md §Sub-phases
**Source material:** SLE-022 (run artifacts & AI context pack)

## Overview

Every validation run produces a structured output directory containing per-category
results, metrics, traces, service logs, and a machine-generated narrative called
`context-pack.md`. The validation review step assembles the narrative deterministically from
structured outputs — no LLM call, no latency. On retry iterations the context
manager injects the narrative as Component 5 so the Planner and Debugger
understand *why* something failed and *where* to look.

The artifact schema is adaptive: different project types declare different
outputs in `validation.yaml → run_artifacts`. A high-performance service emits
latency percentiles and request traces. A library emits only test results and
lint output. The Builder generates scripts that produce the declared outputs.

Run artifacts bridge raw test execution (Layer 4, Docker) and the feedback
loop (Layer 3, Planner/Debugger). They also feed the graph dashboard (SLE-013)
for historical execution traces.

## Data model

### Run directory structure

```
.sle/runs/
  {run_id}/                        ← one directory per validation run
    manifest.json                  ← entrypoint — always present
    ai/
      context-pack.md              ← pre-digested narrative — always present
    tests/
      summary.json                 ← aggregate pass/fail — always present
      {category}/
        result.json                ← per-category structured result
    static-analysis/
      results.json                 ← lint + typecheck + complexity
    metrics/
      {category}.json              ← quantitative metrics per category
    traces/
      {category}.jsonl             ← distributed trace spans per category
    logs/
      {service}.log                ← service logs captured during execution
```

Run ID format: `{workflow_run_id}-i{iteration}-{ISO8601}` — e.g.
`full-build-3-i2-2026-04-07T18-42-10Z`, where `full-build-3` is the parent
`WorkflowRun.run_id` (DDR-031). ISO timestamps replace `:` with `-` for
filesystem safety. This per-iteration validation-run id is distinct from the
stable `WorkflowRun.run_id` used for API addressing across the run's whole
lifetime — see [workflow-execution.md](workflow-execution.md) §Data model.

Runs are retained for the lifetime of the project. The context manager reads
only the most recent run (via `map.yaml → last_run.run_dir`). Old runs are
available for the graph dashboard and historical queries.

### RunManifest

```typescript
interface RunManifest {
  run_id: string
  workflow_run_id: string
  iteration: number
  timestamp: string
  outcome: 'passed' | 'failed'
  failed_categories: string[]
  passed_categories: string[]
  static_analysis: 'passed' | 'failed' | 'skipped'
  quick_summary: string
  artifacts: {
    context_pack: string
    test_summary: string
    static_analysis: string
    categories: Record<string, string>
    logs?: Record<string, string>
    traces?: string
    metrics?: string
  }
}
```

`manifest.json` is the first file the context manager reads when assembling
Component 5. It is a complete index of everything the run produced.

| Field | Always present | Description |
|---|---|---|
| `run_id` | Yes | Unique run identifier matching directory name |
| `workflow_run_id` / `iteration` | Yes | Parent `WorkflowRun.run_id` and position within its iteration lifecycle |
| `outcome` | Yes | `passed` or `failed` |
| `failed_categories` | Yes | Empty array on pass |
| `passed_categories` | Yes | All categories on pass |
| `static_analysis` | Yes | `passed`, `failed`, or `skipped` |
| `quick_summary` | Yes | 1–2 sentence plain-text digest for orientation |
| `artifacts` | Yes | Relative path map — context manager reads this to locate files |

`quick_summary` is generated by code from structured results. The context
manager always includes it — everything else is loaded selectively by category.

### CategoryRunResult

```typescript
interface CategoryRunResult {
  category: string
  phase: 'executable' | 'llm' | 'static'
  passed: boolean
  tests: Array<{
    id: string
    passed: boolean
    expected?: Record<string, unknown>
    actual?: Record<string, unknown>
    message?: string
  }>
  metrics?: Record<string, number>
  duration_ms: number
}
```

Every category's `result.json` must conform to this structure.

The `metrics` block is open — categories define their own metric keys. The gate
reads whatever is present and includes it in `context-pack.md`.

### RunArtifactSchema

```typescript
interface RunArtifactSchema {
  always: Array<{
    path: string
    generated_by: 'gate' | 'static_analysis_phase'
  }>
  categories: Record<string, Array<{
    path: string
    format: 'json' | 'jsonl' | 'junit' | 'text'
    required: boolean
    description?: string
  }>>
  services: {
    enabled: boolean
    path_template: string
    tail_lines: number
  }
  retention: {
    keep_last_n_runs: number
    keep_failed_runs: boolean
    keep_passed_runs: boolean
  }
}
```

Declared in `validation.yaml → run_artifacts`. Different project types declare
different schemas. The Builder receives only the active-category portions as
task constraints.

### FailureReport (updated)

```typescript
interface FailureReport {
  workflow_run_id: string
  iteration: number
  run_dir: string
  run_id: string
  quick_summary: string
  failed_categories: string[]
  passed_categories: string[]
}
```

Replaces the earlier inline `FailureReport` (SLE-002/SLE-003). Carries
`run_dir` and `quick_summary` instead of inline failure detail. The context
manager reads the run directory directly via `run_dir`.

### map.yaml extension

```yaml
last_run:
  run_id: "full-build-3-i2-2026-04-07T18-42-10Z"
  run_dir: ".sle/runs/full-build-3-i2-2026-04-07T18-42-10Z"
  outcome: "failed"
  failed_categories: ["performance", "security"]
  quick_summary: "2/3 categories passed. Performance: p95=340ms..."
  timestamp: "2026-04-07T18:42:10Z"
```

The context manager reads `map.yaml → last_run.run_dir` to locate the most
recent run artifacts when assembling Component 5. It does not search the runs
directory.

### Artifact slice references (G25)

Run artifacts are referenced using typed prefixes per DDR-025:

| Format | Scope | Resolution | Example |
|---|---|---|---|
| `doc:{key}` | Project | `.sle/project-docs/` | `doc:debug-diagnosis` |
| `node:{group}:{key}` | Group | `.sle/project-graph/layers/` | `node:auth:implementation` |

Run-scoped artifacts under `.sle/runs/{id}/` are referenced by their
filesystem path — they are not assigned typed prefixes because they are
ephemeral per-run data, not project-level or group-level documents.

The context manager resolves typed references to file contents within the token
budget. Run artifacts are loaded by the context manager using the `run_dir`
path from `map.yaml → last_run`.

## Behavior

### Run lifecycle

```
1. execute step starts
   │
   ▼
2. Docker container created with $RUN_DIR env var
   │
   ▼
3. static-check sub-phase runs
   ├── PASS → continue to per-category fan-out
   └── FAIL → skip remaining sub-phases, write partial manifest
   │
   ▼
4. Per-category fan-out (parallel across categories)
   │  For each active category:
   │    a. llm-check (if method is 'llm' or 'both')
   │    b. exec-check (if method is 'executable' or 'both')
   │    c. Scripts write to $RUN_DIR per RunArtifactSchema
   │
   ▼
5. Validation review step collects all outputs
   │
   ▼
6. Review step generates manifest.json
   │  - Enumerate all files written to run directory
   │  - Build artifact path map
   │  - Compute quick_summary from structured results
   │  - Set outcome based on category pass/fail
   │
   ▼
7. Review step generates context-pack.md
   │  - Section by section from manifest + raw content
   │  - Failed categories first (detailed), then passed (summary)
   │  - Deterministic — no LLM call
   │
   ▼
8. Review step evaluates pass/fail (pure function)
   │
   ├── PASS → FailureReport not needed
   │          Update map.yaml → last_run
   │          Proceed to the produce step that generates the verdict (EVALUATE)
   │
   └── FAIL → Construct FailureReport with run_dir pointer
              Update map.yaml → last_run
              Proceed to the failure-path produce step (DEBUG), per on_fail routing
```

### context-pack.md generation

The validation review step generates `context-pack.md` section by section. It
is always present even if the run had errors.

**Section order and content:**

| Section | Content | When present |
|---|---|---|
| Summary header | Workflow run/iteration, timestamp, outcome, category counts | Always |
| Per-category — failed | Test results, metrics, trace excerpt, log excerpt | Failed categories first |
| Per-category — passed | Single line: test count only | Passed categories second |
| Static analysis | Lint errors/warnings, typecheck status, complexity | Always |

**Failed category detail:**

1. Test results from `tests/{category}/result.json` — pass/fail per test ID
2. Metrics from `metrics/{category}.json` — quantitative values
3. Trace summary from `traces/{category}.jsonl` — hottest path identification
4. Log excerpt from `logs/{service}.log` — errors/warnings only, last 20 lines

**Passed category detail:**

Single line: "N/N tests passed. No issues." The Planner does not need detail
about what is already working.

**Example (2 failed, 1 passed):**

```markdown
# Run context — full-build-3, Iteration 2
Generated: 2026-04-07T18:42:10Z | Outcome: FAILED

## Summary
2 of 3 categories failed. Static analysis passed.

## Correctness — PASSED
3/3 tests passed. No issues.

## Performance — FAILED
**Tests:** bench:p95_latency FAILED (340ms > 200ms) · bench:error_rate FAILED (0.8% > 0.1%)
**Metrics:** p50=180ms · p95=340ms · p99=620ms · error_rate=0.8%
**Trace:** POST /items → rate-limiter.ts:47 → redis.get() (68% latency)
**Logs:** [18:41:55] WARN Redis latency spike 280ms · [18:41:56] ERROR timeout 300ms

## Security — FAILED
**LLM (0.92):** API key logged at auth.ts:23 · Rate limit counter not shared across instances
**Executable:** security:api_key_exposure FAILED · security:rate_limit_bypass FAILED

## Static analysis — PASSED
Lint: 0 errors, 3 warnings (non-blocking) · Typecheck: clean · Complexity: max=4
```

### Context manager integration (Component 5)

On retry iterations (iteration > 1), the context manager assembles Component 5
from run artifacts:

```typescript
async function buildFailureContext(
  failureReport: FailureReport,
  failedCategories: string[]
): Promise<string> {

  const runDir = failureReport.run_dir
  const orientation = `Run ${failureReport.run_id}: ${failureReport.quick_summary}`
  const contextPack = await readFile(`${runDir}/ai/context-pack.md`)
  const failedSections = extractSections(contextPack, failedCategories)

  return formatFailureContext(orientation, failedSections)
}
```

The context manager checks `manifest.json` before loading — it never assumes a
file is present. It loads only what is declared in the manifest.

**Token budget for Component 5:** ~400 tokens. Per-category: heading + tests
(~80 tokens), metrics (~40), trace/log excerpt (~60). Total ~180 tokens per
failed category. Two failures: ~380 tokens including orientation. For 3+
failures the gate trims sections to fit, keeping test failures and metrics
over traces and logs.

### Builder integration

The Builder receives only the active category requirements from
`run_artifacts.categories`, formatted as a task instruction. It does not see
the full schema, the services section, or the retention policy.

Example task injection:

```
Your test scripts must write outputs to the run artifact directory.
The RUN_DIR environment variable will be set at execution time.

Required outputs for the performance category:
  $RUN_DIR/tests/performance/result.json  — structured pass/fail (JSON)
  $RUN_DIR/metrics/percentiles.json       — p50/p95/p99 latency, error rate

Optional outputs:
  $RUN_DIR/traces/request-map.jsonl       — per-request traces (if available)

result.json must conform to CategoryRunResult schema.
```

### Adaptive schema in validation.yaml

The `run_artifacts` section in `validation.yaml` declares what each validation
run produces. The `always` section lists gate-generated artifacts. The
`categories` section lists per-category outputs that Builder scripts produce.

```yaml
run_artifacts:
  always:
    - path: "ai/context-pack.md"
      generated_by: gate
    - path: "tests/summary.json"
      generated_by: gate
    - path: "static-analysis/results.json"
      generated_by: static_analysis_phase

  categories:
    correctness:
      - path: "tests/correctness/result.json"
        format: json
        required: true
    performance:
      - path: "tests/performance/result.json"
        format: json
        required: true
      - path: "metrics/percentiles.json"
        format: json
        required: true
      - path: "traces/request-map.jsonl"
        format: jsonl
        required: false
    security:
      - path: "tests/security/result.json"
        format: json
        required: true

  services:
    enabled: true
    path_template: "logs/{service_name}.log"
    tail_lines: 500
  retention:
    keep_last_n_runs: 20
    keep_failed_runs: true
    keep_passed_runs: true
```

Service log capture is auto-populated from `map.yaml → services[]`. Logs are
only captured when `services.enabled` is `true` and `map.yaml` declares a
services list.

### Gate node responsibilities

The gate has six sequential responsibilities (expanded from the pre-SLE-022
two-step evaluate-and-report):

1. Evaluate `CategoryResult[]` → pass or fail
2. Collect all run artifact files from Builder script outputs
3. Generate `manifest.json` from collected artifacts + category results
4. Generate `context-pack.md` from manifest + raw artifact content
5. Write both to the run directory
6. Construct `FailureReport` pointing to run directory (not inline content)

The gate validates that all `required: true` artifacts in the schema were
produced. If a required artifact is missing, the gate treats that category as
failed with an auto-generated error message.

### Live updates during execution

Run artifacts are written incrementally during execution. The gate emits
WebSocket events as artifacts are produced:

| Event | Payload | When emitted |
|---|---|---|
| `run.artifact_written` | `{ run_id, path, category? }` | Each artifact file written to disk |
| `run.manifest_ready` | `{ run_id, manifest }` | After manifest.json is generated |
| `run.context_pack_ready` | `{ run_id }` | After context-pack.md is generated |

The Overview panel and graph dashboard listen to these events for live
progress updates during execution.

### Step impact

| Step (kind) | Change from SLE-022 |
|---|---|
| **BUILD** (produce) | Receives run_artifact schema for active categories in task component; generates scripts that write to `$RUN_DIR` |
| **EXEC** (execute) | Scripts execute with `RUN_DIR` env var set; write artifacts to run directory during execution |
| **VALIDATION_GATE** (review) | After evaluating results, generates `manifest.json` and `context-pack.md`; `FailureReport` carries `run_dir` instead of inline content |
| **SNAPSHOT** (commit) | Run directory path included in version snapshot; previous run dirs preserved; `map.yaml → last_run` updated |

The context manager changes are in the assembly path only — no step kind
change is required for context assembly.

## Error cases

### Run generation errors

| Error | Condition | Response |
|---|---|---|
| `required_artifact_missing` | A `required: true` artifact not produced by EXEC scripts | Category treated as failed. Manifest records missing path. |
| `manifest_write_failed` | Filesystem error writing `manifest.json` | Halt the workflow run. Preserve partial run directory. |
| `context_pack_write_failed` | Filesystem error writing `context-pack.md` | Halt the workflow run. Manifest still valid. |
| `run_dir_creation_failed` | Cannot create `.sle/runs/{run_id}/` | Halt the workflow run. EXEC cannot run without run directory. |
| `static_analysis_timeout` | Static analysis exceeds timeout | Skip remaining sub-phases. Write partial manifest. |
| `script_output_invalid` | EXEC output does not conform to `CategoryRunResult` | Synthetic failure entry. Log schema errors. |

### Context manager errors (run-specific)

| Error | Condition | Response |
|---|---|---|
| `run_artifact_missing` | Referenced run artifact does not exist | Load what is available. Log warning. |
| `context_pack_parse_error` | `context-pack.md` is malformed or empty | Fall back to `quick_summary`. Log warning. |
| `run_dir_not_found` | `last_run.run_dir` points to non-existent directory | Halt the workflow run. State inconsistent. Log critical. |
| `manifest_corrupt` | `manifest.json` fails to parse | Fall back to directory listing. Log warning. |

### Gate evaluation errors

| Error | Condition | Response |
|---|---|---|
| `gate_evaluation_error` | Unexpected schema in category results | Halt the workflow run. Log full category result. |
| `partial_run` | EXEC interrupted before all categories completed | Evaluate completed categories only. Incomplete treated as failed. |

### Recovery behavior

Run artifacts are write-once within a run — the gate never overwrites EXEC
output files. If the gate crashes during manifest or context-pack generation,
raw outputs are preserved. On daemon restart, if `last_run` exists but
`manifest.json` is missing, the daemon regenerates it from raw outputs.

## Constraints

1. **Deterministic narrative.** `context-pack.md` is generated by code (the
   validation review step), not by an LLM call. It is consumed *before* the next LLM call
   — making it an LLM artifact would add latency and create a circular
   dependency on the failure path.

2. **No inline FailureReport.** The `FailureReport` no longer carries inline
   failure detail. It carries `run_dir` and `quick_summary`. The context
   manager reads the run directory directly.

3. **Builder isolation from schema.** The Builder receives only the active
   category requirements from `run_artifacts`, formatted as a task instruction.
   It does not see the full schema, the services section, or the retention
   policy.

4. **Required artifact enforcement.** The gate validates that all `required:
   true` artifacts in the schema were produced. Missing required artifacts
   cause the category to fail.

5. **Failed-first ordering.** In `context-pack.md`, failed categories appear
   before passed categories. Passed categories get a single summary line.
   This keeps the Planner and Debugger focused on what needs fixing.

6. **Token budget for Component 5.** The context-pack is budgeted at ~400
   tokens. If 3+ categories fail, the gate trims sections to fit, keeping
   test failures and metrics over traces and logs.

7. **Single run per iteration.** Each iteration produces exactly one run
   directory. The run ID encodes the parent `WorkflowRun.run_id` and the
   iteration number. There are no partial or intermediate runs within an
   iteration.

8. **Run ID encoding.** Run IDs use the format
   `{workflow_run_id}-i{iteration}-{ISO}` with colons replaced by hyphens.
   The ID is filesystem-safe and human-sortable.

9. **Artifact references (G25).** All artifact slice references in context
   assembly use typed prefixes: `doc:{key}` or `node:{group}:{key}` per
   DDR-025. Run-scoped artifacts under `.sle/runs/` are referenced by
   filesystem path — they are not assigned typed prefixes.

10. **map.yaml is the locator.** The context manager locates run artifacts
    through `map.yaml → last_run.run_dir`, never by scanning the runs
    directory. This is O(1) and deterministic.

11. **Incremental writes.** EXEC scripts write artifacts to the run directory
    as they execute. The gate does not buffer all outputs and write at the end.
    This enables live progress via WebSocket events.

12. **Retention policy.** Runs are retained per `validation.yaml →
    run_artifacts.retention`. Failed runs are always kept regardless of the
    `keep_last_n_runs` setting. The daemon prunes old runs only when a new run
    is created.

13. **Docker isolation.** All EXEC sub-phases run inside a fresh Docker
    container per iteration. Scripts receive `$RUN_DIR` as an environment
    variable pointing to a mounted volume.

14. **Static analysis gate.** `static-check` runs once per iteration (not per
    category). If it fails, `llm-check` and `exec-check` are skipped entirely.
    The manifest records `static_analysis: failed` and only the static-analysis
    artifacts are present.

15. **Crash recovery.** If the daemon crashes during EXEC, the partial run
    directory is preserved. On restart the daemon detects the incomplete run
    via `map.yaml → last_run` and either retries or halts per exit config.

## Open questions

| ID | Question | Impact | Status |
|---|---|---|---|
| RA-001 | Should `context-pack.md` generation be configurable via templates, or is the hardcoded section order sufficient? | Flexibility for non-standard project types | Open |
| RA-002 | What is the maximum total disk size for a single run directory before the system should warn or halt? | Resource management, disk exhaustion prevention | Open |
| RA-003 | Should the gate support streaming `context-pack.md` generation for runs with many (10+) failed categories? | Performance, memory usage for large validation suites | Open |
| RA-004 | Should run artifacts be compressed (tar.gz) when retained beyond the `keep_last_n_runs` threshold? | Long-term storage efficiency | Open |
| RA-005 | How should the gate handle a category with valid JSON but semantically nonsensical results? | Gate robustness | Open |
| RA-006 | Should run directories be committed to the docs remote alongside version snapshots? | Team visibility, CI | Open |
